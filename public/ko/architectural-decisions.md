# 기술적 근거

## 1. 분산 프론트엔드 -> 모노레포

**문제:** 웹, 모바일, 어드민, 웹뷰 작업이 여러 레포에 흩어져 있었습니다. 공유 타입과 유틸리티가 드리프트했고, 크로스 플랫폼 변경에는 조율 비용이 컸습니다.

**결정:** 프론트엔드 운영 레이어를 단일 모노레포로 통합했습니다.

**임팩트:** 2026-05-19 기준 모노레포 작성 PR 1,130건. 공유 패키지, 일관된 리뷰 패턴, 한 곳에서 고치는 타입 수정이 이후 성능, SEO, 릴리스 작업을 안전하게 만들었습니다.

## 2. 검색에 보이지 않는 웹 -> SSR

**문제:** 중요한 공개 페이지들이 검색엔진이 안정적으로 색인하기 어려운 CSR/정적 구조였습니다.

**결정:** 공개 웹 경험을 SSR, 동적 사이트맵, 구조화 데이터, 서버 렌더링 가능한 프로덕션 호스팅 기반으로 전환했습니다.

**임팩트:** 사이트맵 범위가 5개 URL에서 48,706개 매물/아파트 URL로 확장되었습니다. 이후 SEO와 AI 검색 대응 작업의 기반이 되었습니다.

## 3. 느린 공개 웹 -> 성능 캠페인

**문제:** 공개 웹의 PageSpeed는 약 20이었고 렌더링을 막는 코드 경로가 많았습니다.

**결정:** 전체 rewrite가 아니라 단계적 성능 캠페인을 실행했습니다. SSR waterfall 제거, LCP 최적화, 무거운 SDK lazy load, 번들 축소, perceived loading 개선으로 나눴습니다.

**임팩트:** [PageSpeed가 80](https://pagespeed.web.dev/analysis/https-bootalk-co-kr/4jic9i7it6?form_factor=desktop)까지 올라갔습니다. 작은 단위의 가역적 단계로 나누었기 때문에 운영 중인 제품에서도 배포 가능했습니다.

## 4. 수동 에러 분석 -> AI 운영 workflow

**문제:** 프로덕션 에러량이 늘어나면서 수동 분석은 비용이 크고 일관성이 떨어졌습니다.

**결정:** 모니터링 이벤트를 AI 기반 진단 및 PR 생성 workflow와 연결하되, merge 전 사람의 리뷰를 유지했습니다.

**임팩트:** 에러 대응이 임시 조사에서 반복 가능한 운영 파이프라인으로 바뀌었습니다.

## 5. AI 프로토타입 -> 상용 인도

**문제:** [세무GPT](https://semugpt.co.kr)는 프로토타입을 넘어 클라이언트가 운영 가능한 프로덕션 제품이 되어야 했습니다.

**결정:** 프로덕션화를 제품 자체로 다뤘습니다. 권한 로직, 결제/웹훅, 평가, 관측성, CI/CD, runbook, 인수인계, 전환 준비를 함께 묶었습니다.

**임팩트:** 2026-05-18 [세무GPT](https://semugpt.co.kr) 클라이언트 인수인계가 완료되었고 상용 계약이 체결되었습니다.

## 복리 구조

```text
모노레포 -> 타입/릴리스 안전성 -> SSR -> 성능 -> 모니터링 -> AI 운영 -> 상용 인도
```

중요한 것은 순서입니다. 각 결정은 다음 결정의 비용과 리스크를 낮췄습니다.
